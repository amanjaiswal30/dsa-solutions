Server-side, API Gateway level. Limit per user ID. 10 million users, free tier gets 60 req/min, paid gets 1000. Peak around 1.5 million req/sec across the platform. Return 429 with standard headers. Burst — yes, paid users should be able to spike.
REQUIREMENTS
FR + NFR — always write these out loud
YOU
YouFR + NFR
Functional:
  • Limit N requests per minute per userId — configurable per tier
  • HTTP 429 on breach with headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After
  • Burst support for paid users
  • Allowlist for internal services
Non-Functional:
  • Latency: <5ms added to every request — this is in the hot path
  • Availability: if the limiter is down, fail open — never block production traffic because the limiter failed
  • Consistency: eventual is fine — small over-allowance at window boundaries is acceptable
  • Scale: 10M users, 1.5M req/sec — needs very fast shared state
API DESIGN
What does the interface look like?
YOU
YouAPI Contract
The rate limiter is middleware — not a standalone API. Every inbound request passes through it before hitting any service. The interface is:
  • isAllowed(userId, endpoint) → {allowed: bool, remaining: int, resetAt: epoch}
  • On allowed=false: gateway returns 429, sets response headers, does NOT forward request
  • On allowed=true: gateway forwards, decrements counter in background
For the rules API (admin updating tier limits):
  • PUT /rl/rules/{tier} → {limit, windowSec, burstCapacity}
  • Changes propagate to all gateway nodes within 30 seconds
PHASE 1
Single server — start simple
Architecture Diagram
YOU
YouSingle Server Design
Simplest design: one API server, in-memory HashMap on that server.
  • Key: userId, Value: {count, windowStart}
  • On each request: if now - windowStart > 60s, reset. If count < limit, increment and allow. Else 429.
  • O(1) lookup, zero network calls, sub-millisecond.
Why HashMap
O(1) average lookup and insert. Thread-safe with ConcurrentHashMap. No serialization overhead. Perfect for in-process state.
INT
InterviewerProbe — Scale
We run 200 API servers behind the load balancer. What breaks?
YOU
YouIdentifying Bottleneck
The counters are local to each server. User A sends 200 requests — load balancer distributes them, so each server sees ~1 request. Every server's counter is 1, limit is 60, all pass. The rate limit is effectively multiplied by 200. We need shared state visible to all servers.
PHASE 2
Add Redis — centralized shared counter
Architecture Diagram
YOU
YouRedis Design
Replace the local HashMap with Redis. All API servers share one Redis — counters are consistent across the fleet.
Why Redis specifically
Redis is single-threaded — operations are inherently atomic. INCR returns the new value atomically, no compare-and-swap needed. Sub-millisecond latency. Supports TTL natively. ~200K ops/sec on a single node.
Now let me think about the algorithm. I have a few options:
  • Fixed Window Counter — simplest, but has a boundary burst problem
  • Sliding Window Log — exact, but memory heavy
  • Sliding Window Counter — good balance, my default choice
  • Token Bucket — best for burst support which paid users need
I'll use Sliding Window Counter as baseline, and Token Bucket for paid users with burst.
INT
InterviewerProbe — Redis Key
What exactly does the Redis key look like? What data type? What's the TTL?
YOU
YouKey Design
For Sliding Window Counter — I split the 60s window into 6 buckets of 10s each:
  • Key: rl:swc:{userId}:{floor(epoch_ms / 10000)}
  • Example: rl:swc:u9182:171724322
  • Type: String (integer counter)
  • Commands: INCR key on each request, EXPIRE key 120 (keep 2 windows)
  • Read: MGET of 6 consecutive bucket keys, sum them
  • TTL: 120s — two full windows so we don't lose data at window edge
Why floor(epoch / 10000) in the key
This makes the bucket key deterministic and identical across all API servers without coordination. Server A and Server B compute the same bucket key for the same timestamp because they both just do the same integer division. Clock drift of <1ms (NTP guarantee) is irrelevant at a 10s bucket granularity.
Why String not Hash or List
INCR only works on String type. It's atomic and returns the new value in one operation. Using a Hash would require HINCRBY + HGET — two operations, or a Lua script. String + INCR is the simplest atomic solution.
For Token Bucket (paid users, burst support):
  • Key: rl:tb:{userId}
  • Type: Hash with fields t (float tokens remaining) and r (last refill epoch ms)
  • Must use a Lua script for atomicity — HMGET + compute + HMSET is not atomic otherwise
🔴 Lua Script — Token Bucket (atomic read-modify-write)
-- KEYS[1]="rl:tb:{userId}"
-- ARGV: capacity, rate(tokens/sec), now_ms, cost
local data    = redis.call('HMGET', KEYS[1], 't', 'r')
local tokens  = tonumber(data[1]) or tonumber(ARGV[1])
local last    = tonumber(data[2]) or tonumber(ARGV[3])
local elapsed = (tonumber(ARGV[3]) - last) / 1000.0
tokens = math.min(tonumber(ARGV[1]), tokens + elapsed * tonumber(ARGV[2]))
if tokens < tonumber(ARGV[4]) then
  return {0, math.ceil((tonumber(ARGV[4])-tokens)/tonumber(ARGV[2])*1000)}
end
tokens = tokens - tonumber(ARGV[4])
redis.call('HMSET', KEYS[1], 't', tokens, 'r', ARGV[3])
redis.call('EXPIRE', KEYS[1], 3600)
return {1, 0}   -- {allowed, retry_after_ms}
Why Lua and not MULTI/EXEC
MULTI/EXEC (transactions) still requires sending multiple round trips. Lua runs server-side as a single atomic operation — no round trips between read and write. Also preload with SCRIPT LOAD and call via EVALSHA for zero parsing overhead per call.

PHASE 3
Scale Redis — cluster + local cache
Architecture Diagram
YOU
YouRedis Cluster
Two moves here:
  • Redis Cluster — shard by userId. Consistent hash on userId means all rl:{userId}:* keys for one user land on the same shard. No cross-shard ops needed per request.
  • L1 in-process cache — Caffeine LRU cache on each API server, keyed by userId, TTL 100ms. On cache hit: no Redis call at all. At ~80% hit rate this cuts Redis ops from 1.5M/sec to ~300K/sec across the fleet.
Why shard by userId and not by endpoint
All rate limit keys for one user must be on the same shard so a single MGET can fetch all 6 bucket keys in one roundtrip. If we sharded by something else, a single user's 6 bucket keys might span multiple shards, requiring multiple roundtrips.
Why 100ms TTL on L1 cache
100ms over-allowance is acceptable per NFR (eventual consistency). At 60 req/min = 1/sec, 100ms = 0.1 extra request possible — negligible. But 100ms TTL reduces Redis pressure by ~80% for high-frequency callers. The tradeoff is explicitly in our NFR.
INT
InterviewerProbe — Redis Down
What happens if a Redis shard goes down?
YOU
YouFail-Open Strategy
Fail open — never fail closed. If Redis is unavailable, the API server falls back to the L1 Caffeine cache only. Requests may slightly exceed limits during the degradation window (typically <30s until replica promotion). We emit a rate_limiter.degraded_mode=true metric and alert on-call. This is a deliberate tradeoff — a rate limiter outage must not become a service outage.
Why fail-open not fail-closed
Failing closed (blocking all requests when Redis is down) would take the entire product offline every time Redis has a hiccup. The purpose of a rate limiter is to protect against abuse — occasional over-allowance during a 30-second Redis failover is vastly preferable to taking the whole platform down.

Why PostgreSQL for rules, not Redis
Rules are written infrequently by admins — strong consistency and durability matter more than speed. PostgreSQL gives us ACID, a schema, and audit history. Redis is the read cache (30s TTL) and pub/sub for invalidation. DB is source of truth; Redis is the fast path.

System Design Interview — Topic 02 of 09
Consistent Hashing
Distribute data across nodes so adding or removing a node reshuffles ~1/N keys instead of ~100%.
Ring HashVirtual NodesTreeMap O(log N)Preference ListW+R>N Quorum
OPENING
INT
InterviewerOpening
We have a 10-node cache cluster. Every time we add a single node, our cache hit rate crashes to near zero for 30 minutes. Figure out why and fix it.
CLARIFICATION + ROOT CAUSE
YOU
YouDiagnosing the Problem
I know exactly what's happening — you're using modulo hashing: node = hash(key) % N. When N changes from 10 to 11, the formula changes for nearly every key. Specifically ~(N-1)/N ≈ 91% of all keys remap to a different node simultaneously. The entire cache goes cold at once. We need consistent hashing.
The Math
key with hash 4,829,301: 4829301 % 10 = 1 (Node 1). Add a node: 4829301 % 11 = 7 (Node 7). Moved. This happens for ~91% of keys the moment N changes by 1.
PHASE 1
Consistent Hash Ring — basic concept
Architecture Diagram
YOU
YouCore Idea
Imagine a ring with positions 0 to 2³²-1. Hash each server's name/IP to a position on the ring. Hash each key to a position. The key's owner is the first server you hit walking clockwise from the key's position. When you add Server D, it claims a position. The only keys that move are those between D and its counter-clockwise predecessor — roughly K/N keys. Everything else is untouched.
Why This Works
Adding/removing a node only affects the adjacent arc, not the entire key space. ~1/N keys move vs ~91% with modulo.
INT
InterviewerProbe — Uneven Load
What if Server A happens to own 60% of the ring? One server does all the work.
PHASE 2
Virtual Nodes — even distribution
Architecture Diagram
YOU
YouVirtual Nodes
That's the key weakness of a basic ring with few servers — arc sizes are random and can be wildly uneven. Fix: virtual nodes. Instead of one ring position per server, we assign each physical server 150 positions. Hash "ServerA-0", "ServerA-1", ..., "ServerA-149" — each lands at a different ring position. The physical server owns whichever real keys fall in any of its 150 arcs. Now load is near-uniform because each server has many small scattered arcs. When a server fails, its 150 arcs each shift to a different successor — load spreads across all peers, not one.
Why 150 vnodes specifically
At 150 vnodes per server, standard deviation of load across servers is <5%. Below 50: unacceptable unevenness. Above 300: diminishing returns. 150–256 is the production sweet spot — Cassandra uses 256 by default.
INT
InterviewerProbe — Implementation
How do you actually look up which server owns a key? What data structure, what's the complexity?
YOU
YouTreeMap Implementation
TreeMap<Long, ServerNode> — keys are ring positions (uint64 hash), values are server references. The map is kept sorted. Lookup is: ring.ceilingEntry(hash(key)) — returns the smallest position ≥ hash. If null (hash is past the last entry): ring.firstEntry() to wrap around. That's the owning server. O(log N) where N = total vnode count. With 3 servers × 150 vnodes = 450 entries → log₂(450) ≈ 9 comparisons. Negligible.
💻 TreeMap Operations
// Add a server (150 vnodes)
for (int i = 0; i < NUM_VNODES; i++) {
  long pos = hash(server.id + "-" + i);
  ring.put(pos, server);
}

// Remove a server
for (int i = 0; i < NUM_VNODES; i++) {
  ring.remove(hash(server.id + "-" + i));
}

// Lookup: which server owns key K?
long pos = hash(key);
Map.Entry<Long, Server> e = ring.ceilingEntry(pos);
Server owner = (e != null) ? e.getValue() : ring.firstEntry().getValue();

InterviewerProbe — Replication
How do you replicate data for fault tolerance using this ring?
PHASE 3
Preference List — DynamoDB-style replication
Architecture Diagram
YOU
YouReplication Strategy
Preference list. For key K, the primary is the first server clockwise (owner). The replicas are the next N-1 servers clockwise, skipping vnodes of the same physical server. So if N=3: primary + 2 replicas on 3 distinct physical machines. For writes: require W=2 nodes to acknowledge. For reads: read from R=2 nodes. W+R=4 > N=3 → at least one node is in both sets → reads always see the latest write → strong consistency.
Why W=2 R=2 specifically
W+R > N is the quorum condition for strong consistency. W=1,R=1: max availability, eventual consistency. W=3,R=1: max write durability. W=2,R=2 is the balanced middle ground — tolerates one node failure while maintaining consistency.
For always-writable behavior (Dynamo-style): use sloppy quorum — if the primary is down, next healthy node accepts the write with a "hint." When primary recovers, hinted handoff replays the buffered writes.
INT
InterviewerWhere is this used?
Where does this show up in real systems you know?
YOU
YouReal-World Examples
  • Cassandra — token ring, 256 vnodes per node by default. Each node owns a token range.
  • DynamoDB — preference list with N=3, hinted handoff, always-writable.
  • Redis Cluster — 16,384 fixed hash slots (conceptually the same thing with a fixed ring size). Each node owns a range of slots.
  • Memcached — client-side ketama library implements consistent hashing with 160 vnodes/server.
In my current work on API Gateway at Workday — our Rate Limiter shards Redis by userId using consistent hashing so all keys for a user always land on the same shard.
🔢 Algorithm
  • Ring: 0 to 2³² positions
  • Hash server + key → ring position
  • Owner: first server clockwise
  • Add/remove: ~1/N keys move
  • 150–256 vnodes per physical server

PHASE 1
Single node — what storage engine?
Architecture Diagram
YOU
YouStorage Engine Choice
10TB means we can't use a pure in-memory HashMap — that would need 10TB of RAM. We need a disk-based storage engine. Two main choices: B-Tree (MySQL, Postgres) or LSM Tree (RocksDB, Cassandra). For 100K writes/sec, I'll go LSM Tree.
Why LSM Tree over B-Tree
B-Tree does random in-place page updates on disk — each write potentially rewrites multiple B-tree pages → write amplification → ceiling of ~10–50K writes/sec on SSD. LSM Tree always writes sequentially — WAL append → Memtable insert → SSTable flush. Sequential writes are 10–100× faster than random writes. At 100K writes/sec, LSM is the only viable choice.
INT
InterviewerProbe — LSM Write Path
Walk me through the write path in an LSM Tree. What happens step by step when I call put("key", "value")?
YOU
YouLSM Write Path
  • Step 1 — WAL: Append the write to the Write-Ahead Log — a sequential, append-only file on disk. This is for crash recovery. If the server dies right after this, the WAL can be replayed on restart.
  • Step 2 — Memtable: Write to the in-memory Memtable — a sorted structure (Red-Black Tree or SkipList). O(log n) insert. This is where the actual data lives while it's hot. We ACK the client here — after Memtable write, not after disk flush.
  • Step 3 — SSTable Flush: When Memtable reaches a size threshold (typically 64MB), it's flushed to disk as an immutable SSTable — a Sorted String Table. During flush we also build a Bloom Filter and a sparse index for that SSTable.
  • Step 4 — Compaction: Background process merges SSTables — removes duplicates, purges tombstones (deletes), keeps data sorted. Leveled compaction (RocksDB default) keeps each level's total size bounded, improving read performance.
Delete is a special case — it writes a tombstone marker. The key appears absent on reads. Physical deletion happens during compaction.
Why ACK after Memtable, not SSTable flush
Flushing to SSTable takes ~seconds (64MB write). Waiting for that would give us terrible write latency. The WAL in step 1 gives us durability — even if we crash between Memtable and SSTable, we can replay the WAL. So it's safe to ACK after the faster Memtable write.
INT
InterviewerProbe — Read Path
Now the read path. get("key") — walk me through it. 10TB means many SSTables on disk — how do you avoid reading all of them?
YOU
YouLSM Read Path + Bloom Filter
Read path checks in order from newest to oldest:
  • 1. Memtable — in-memory, O(log n) lookup. If found, return it (most recent version).
  • 2. Block Cache — recently read SSTable blocks cached in RAM (LRU). Hot keys served entirely from here.
  • 3. Bloom Filter per SSTable — before touching disk, check the Bloom Filter. If it says "definitely not here" → skip this SSTable. If "maybe here" → read from disk. A Bloom Filter with 1% false positive rate eliminates ~99% of unnecessary disk reads for missing keys.
  • 4. SSTable binary search — use the sparse index to find the approximate byte offset, then binary search within that block on disk.
Why Bloom Filter — the key insight
Most get() calls for missing keys would otherwise require reading every SSTable on disk. Bloom Filter is a probabilistic bit array: set bits for every key on SSTable creation. On query: if any hash position is 0 → key DEFINITELY absent → skip this SSTable entirely. Zero false negatives. ~1% false positives (still need to read disk occasionally). This is what makes LSM reads practical at scale.

PHASE 2
Distribute — consistent hashing + quorum
Architecture Diagram
Architecture Diagram
YOU
YouDistribution Design
Consistent hashing on the key — partition the data across N nodes with 150 vnodes per node for even distribution. For replication: DynamoDB-style preference list. N=3, primary + 2 replicas on distinct physical nodes. Write to W=2, read from R=2. W+R=4 > N=3 → strong consistency when all nodes are up.

For membership and failure detection: Gossip protocol. Each node pings K random peers every ~1s, exchanges membership state. Information spreads in O(log N) rounds. No central coordinator.
Why no central coordinator for membership
A central coordinator is a single point of failure and a bottleneck. Gossip is fully decentralized — any node can go down without affecting membership propagation. Convergence in O(log N) rounds means a 1000-node cluster stabilizes in ~10 rounds (~10 seconds), which is fast enough for failure detection.
INT
InterviewerProbe — Conflicts
Network partition. Two replicas accept concurrent writes to the same key. How do you reconcile?
YOU
YouConflict Resolution
Two options: Last-Write-Wins (LWW) — each write gets a wall-clock timestamp, on conflict the higher timestamp wins. Simple, rare data loss on true concurrent writes. Or Vector Clocks — each write tagged with {nodeId → counter}. On read: if one version's vector dominates the other, take the newer one. If neither dominates (truly concurrent), surface both to the caller for application-level resolution — DynamoDB's approach. I'd default to LWW for simplicity unless the application explicitly needs conflict detection.

  • Delete = tombstone marker (physical rm in compaction)
🔍 LSM Read Path

  • Block Cache (hot SSTable blocks in RAM)
  • Bloom Filter: ~99% skip on miss (key insight)
  • Sparse Index → binary search within block
  • Leveled compaction reduces read amplification

PHASE 1
Options evaluation — rule out the bad ones
Architecture Diagram
YOU
YouEvaluating Options
Let me quickly rule out alternatives:
  • DB auto-increment — single DB = SPOF, ~10K IDs/sec ceiling. Doesn't scale multi-DC.
  • UUID v4 — 128-bit, not sortable, random → B-tree fragmentation as a PK. Not what we want.

INT
InterviewerProbe — Bit Layout
Walk me through the Snowflake bit layout. Why is each field sized the way it is?
YOU
YouBit Layout Rationale
64 bits total:
  • Bit 63 (1b) — Sign: Always 0. Java's long is signed — bit 63=1 means negative. Keeping it 0 ensures all IDs are positive longs. No casting needed.
  • Bits 22–62 (41b) — Timestamp: Milliseconds since a custom epoch (e.g. 2020-01-01). 2⁴¹ ms = 69.7 years. We pick a recent epoch to maximize the usable window.
  • Bits 17–21 (5b) — Datacenter ID: 0–31 = 32 DCs. Assigned at deploy time. Static at runtime. Prevents cross-DC collisions.
  • Bits 12–16 (5b) — Worker ID: 0–31 per DC = 1024 total generators. Assigned by ZooKeeper at startup. Prevents within-DC collisions.
  • Bits 0–11 (12b) — Sequence: 0–4095 per millisecond. Auto-increment per request, reset on new ms. 4096 × 1024 = 4.2B IDs/sec cluster-wide.
INT
InterviewerProbe — Machine ID
Two workers start simultaneously and both try to claim machine ID 17. What prevents duplicate IDs?
YOU
YouZooKeeper Assignment
ZooKeeper. Each worker creates an ephemeral sequential ZNode at /id-gen/workers/worker- on startup. ZK appends a globally unique monotonically increasing integer. Worker reads its ZNode's sequence number, uses it as machineId % 1024. ZK guarantees no two nodes get the same number. On crash: ephemeral ZNode auto-deletes (ZK session timeout ~5s) → ID recycled for the next worker. At any moment, no two live workers share a machineId.
Why ZooKeeper only at startup, not per ID
If ZK were consulted per ID generation, we'd have a network call on every request — killing the sub-microsecond goal. ZK is only used once per worker lifecycle (startup). After that, the worker generates IDs purely locally. ZK goes down → no impact on ID generation for running workers.
INT
InterviewerProbe — Clock Skew
NTP corrects the clock backward by 5ms on a generator node. What happens?
YOU
YouClock Skew Handling
We track lastTimestamp in memory. Before generating each ID: currentMs = monotonicClock.now(). If currentMs < lastTimestamp:
  • Small drift (≤10ms): spin-wait until clock catches up. Max added latency: 10ms on rare NTP correction. Log the event.
  • Large drift (>10ms): throw ClockSkewException and alert. This indicates a system problem — NTP misconfiguration, VM time jump, hardware issue. Fail loudly rather than silently generate duplicate IDs.
Use monotonic clock (CLOCK_MONOTONIC) for comparisons — it never goes backward even during NTP adjustments. Use wall clock only for the actual timestamp value embedded in the ID.

InterviewerProbe — DLQ + Idempotency

YouDLQ + Idempotency
On 503: exponential backoff — wait 1s, retry. Wait 2s, retry. Wait 4s, final attempt. After 3 failures: publish to notif-push-dlq with full payload + metadata. Idempotency keys are typically UUIDs in 3rd party APIs (FCM, SendGrid). Using UUID natively as our PK avoids translation. The notifications table is not a time-series table where sort order matters for queries — we query by status or user_id — so UUID randomness doesn't hurt index performance the way it would in a sequential-insert table.

InterviewerProbe — Deduplication
How do you prevent crawling the same URL twice? And how do you detect duplicate content at different URLs?
YOU
YouTwo-Layer Dedup
URL dedup — Bloom Filter: Before adding any URL to the Kafka frontier, check a Bloom Filter. At 1B URLs with 1% false positive rate: ~1GB RAM. If "definitely not seen" → add to frontier. If "maybe seen" (1% false positive) → skip. False positives mean occasionally skipping an unseen URL — rare and acceptable. Zero false negatives mean we never miss URLs we've definitely seen. For high-value URLs, back the Bloom Filter with a Redis Set for exact recent dedup (last 24h).

Content near-dedup — SimHash: Two URLs can have nearly identical content (e.g., same article syndicated across 100 sites). SimHash: compute a 64-bit fingerprint of the page content. Store fingerprints in Cassandra. Before indexing a new page: compare its SimHash with stored fingerprints. If Hamming distance < 3 (meaning ≥61 of 64 bits match): near-duplicate → skip indexing. This catches "99% similar" content that exact hash would miss.

  last_crawled_at   TIMESTAMP,
  http_status       INT,
  content_hash      TEXT,      -- SHA256(content) for exact dedup
  content_simhash   BIGINT,    -- SimHash(content) for near-dup
  crawl_interval_s  INT,       -- recrawl frequency (scheduler updates)
  page_rank         FLOAT,
  PRIMARY KEY (url_fingerprint)
);
CREATE TABLE domain_politeness (
  domain            TEXT  PRIMARY KEY,
  last_crawled_at   TIMESTAMP,
  crawl_delay_sec   INT   DEFAULT 1,  -- from robots.txt
  robots_txt        TEXT,             -- cached content
  robots_cached_at  TIMESTAMP
);
Why Cassandra for crawl metadata
Cassandra: write-heavy (updating last_crawled_at for 1B URLs frequently), simple PK lookup by url_fingerprint, horizontal scale, no complex queries needed. MySQL would struggle with 1B rows at this write frequency. The access pattern is always "does this URL exist, and when was it last crawled" — perfect for Cassandra's PK lookup.

InterviewerProbe — robots.txt + Politeness
How do you honor robots.txt at scale without adding latency to every fetch?
YOU
YouPoliteness Strategy
Cache robots.txt per domain in Cassandra domain_politeness table, TTL 1hr. Before crawling any URL from a domain: check the cached robots.txt. If cache miss: fetch robots.txt first (before crawling any page from that domain). Parse Disallow rules and Crawl-Delay.

Enforce politeness at the Fetcher worker level: since Kafka is partitioned by domain, each Fetcher instance owns specific domains. It simply sleeps max(crawl_delay, 1000/max_rps) ms between consecutive requests to the same domain. No distributed coordination needed — domain isolation is free from the Kafka partition design.

Circuit breaker: if a domain returns 5xx for 10 consecutive requests → pause crawling that domain for exponential backoff (5min, 10min, 20min...).

🗄 MySQL — files + versions (shard key: user_id)
CREATE TABLE files (
  file_id            BIGINT       PRIMARY KEY,  -- Snowflake
  user_id            BIGINT       NOT NULL,     -- owner, SHARD KEY
  parent_folder_id   BIGINT       DEFAULT NULL, -- NULL = root
  name               VARCHAR(255) NOT NULL,
  mime_type          VARCHAR(100),
  current_version_id BIGINT,                   -- FK → file_versions
  is_deleted         TINYINT(1)   DEFAULT 0,
  created_at         DATETIME(3)  DEFAULT NOW(3),
  updated_at         DATETIME(3)  DEFAULT NOW(3) ON UPDATE NOW(3),
  INDEX (user_id, parent_folder_id),            -- "list folder contents"
  INDEX (user_id, updated_at DESC)              -- "recent files" / sync delta
) ENGINE=InnoDB;

CREATE TABLE file_versions (
  version_id   BIGINT   PRIMARY KEY,    -- Snowflake
  file_id      BIGINT   NOT NULL,
  version_num  INT      NOT NULL,
  size_bytes   BIGINT   NOT NULL,
  chunk_ids    JSON     NOT NULL,       -- ordered array of chunk SHA256s
  created_by   BIGINT   NOT NULL,
  created_at   DATETIME(3) DEFAULT NOW(3),
  INDEX (file_id, version_num DESC)     -- version history page
) ENGINE=InnoDB;

CREATE TABLE chunks (
  chunk_id     VARCHAR(64) PRIMARY KEY, -- SHA256(chunk_bytes) = content-addr
  s3_key       TEXT        NOT NULL,   -- S3 object path
  size_bytes   INT         NOT NULL,
  ref_count    INT         DEFAULT 1   -- dedup: how many versions use this chunk
) ENGINE=InnoDB;

CREATE TABLE file_permissions (
  permission_id  BIGINT      PRIMARY KEY,
  file_id        BIGINT      NOT NULL,
  grantee_id     BIGINT      NOT NULL,
  grantee_type   VARCHAR(10) NOT NULL,    -- 'user'|'group'|'public'
  access_level   VARCHAR(10) NOT NULL,   -- 'viewer'|'commenter'|'editor'
  created_at     DATETIME(3) DEFAULT NOW(3),
  UNIQUE (file_id, grantee_id),
  INDEX (grantee_id, file_id)            -- "shared with me" view
) ENGINE=InnoDB;
Why shard by user_id not file_id
"List my files in folder X" is the most common query — it needs all files owned by a user. If we shard by user_id, all of a user's files are on one shard → single shard query, no cross-shard join. If we sharded by file_id, listing a user's files would require fan-out across all shards and aggregation. The tradeoff: a power user with millions of files creates a hot shard. Mitigate with sub-sharding (user_id % N) or cell-based architecture.
Why chunk_id = SHA256(chunk_bytes) — content-addressing
Two users who upload the same file share the same chunks. chunk_id = SHA256(chunk) means both file_versions records point to the same S3 object. ref_count tracks how many versions reference a chunk. Garbage collection: when ref_count reaches 0, delete the S3 object. This is how Google Drive achieves significant storage savings — identical chunks across users and versions are stored exactly once.
INT
InterviewerProbe — Upload Flow
Walk me through the exact upload flow step by step. Where do the bytes go?
YOU
YouUpload Flow
  • 1. Client splits file into 4MB chunks. Computes SHA256(chunk) for each. Sends POST /files/init with {name, chunk_hashes[]}.
  • 2. Metadata Service checks the chunks table: which chunk_ids already exist (ref_count > 0 = already stored). Returns pre-signed S3 URLs only for missing chunks. Already-existing chunks: no upload needed.
  • 3. Client uploads missing chunks directly to S3 via pre-signed URLs. No bytes go through our servers. S3 handles the bandwidth. Parallel uploads: up to 5 chunks simultaneously.
  • 4. Client calls POST /files/{file_id}/complete. Metadata Service: INSERT into file_versions with the ordered chunk_ids array, UPDATE files.current_version_id, UPDATE chunks.ref_count for all chunks.
  • 5. Kafka event published to file-events topic. Notification Service consumes → WebSocket push to collaborators.
Resume on failure: If the upload is interrupted, client re-calls POST /files/init with the same chunk_hashes. Server returns pre-signed URLs for still-missing chunks. Client re-uploads only those. Never re-uploads completed chunks.
Why pre-signed URLs (client → S3 direct)
Without pre-signed URLs, all file bytes would go: Client → Our Server → S3. Our server becomes a bandwidth proxy — needs massive network capacity, adds latency, and costs compute just to pass bytes through. Pre-signed URLs let S3 handle the bandwidth directly. Our server only handles tiny metadata API calls. S3 verifies the signature and stores the chunk. We never see the bytes.
INT
InterviewerProbe — Desktop Sync
Desktop client has 50,000 files. User edits one file. How does the sync client know what changed, and how does it minimize bandwidth?
YOU
YouDelta Sync
What changed — event-driven + checkpoint sync: Sync client subscribes to WebSocket events. When a file changes, Notification Service pushes {file_id, new_version_id} immediately. Client doesn't need to poll. For reconnect after offline: GET /sync?since={last_checkpoint} returns all files with updated_at > checkpoint. That's the INDEX (user_id, updated_at DESC) on the files table — fast range query on one shard.

Minimize bandwidth — delta chunks: When file_versions.chunk_ids changes between version N and N+1, only some chunks differ. The sync client downloads only the chunk_ids in version N+1 that aren't already in its local cache (it tracks which chunk SHA256s it has locally). For a 100MB file where only 4MB changed: only 1 chunk is downloaded, not the full file. 96% bandwidth saved.
Why chunk-level delta sync, not byte-level diff
Byte-level diff (rsync algorithm) is more bandwidth efficient but requires server-side computation of the diff per file per client. At billions of files this is expensive server-side. Chunk-level delta: the client already knows its local chunks (SHA256s), the server returns the new chunk list, client figures out which are missing. Zero server-side computation, purely client-driven. 4MB chunks means typical edits change 1–3 chunks, achieving 90%+ bandwidth savings.

InterviewerFinal Probe
Two users edit the same file simultaneously. How do you handle the conflict?
YOU
YouConflict Resolution
Google Drive's approach for binary files: last-write-wins at the version level, with explicit conflict notification. If both users save simultaneously: both create new version records. The system detects a conflict (both versions have the same parent version_id). The user who saves second is notified: "A conflict was detected. Your changes are saved as version N. [Other user]'s version is M. You can compare both versions." User manually resolves. We keep both versions in history. For text files where real-time co-editing is needed (Docs), that's a separate system using operational transforms — outside scope here.
